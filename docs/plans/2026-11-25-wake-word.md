# "Hey CARL" wake word: design and plan

Approved by the user on 2026-11-25. Training in Colab and the two firmware dependencies (`esp-tflite-micro` and TensorFlow's audio microfrontend, both Apache-2.0) were approved the same day.

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. **Phase 0 is a feasibility test.** Don't start Phase 1 until the user has seen its numbers and agreed.

## Goal

Saying "Hey CARL" wakes the robot with no key press. Detection runs **on the robot** (ESP32-S3) with a microWakeWord model we train ourselves. After a reply, CARL keeps listening for a short follow-up. Push-to-talk stays, and the key always wins.

## Decisions

- **Engine:** **microWakeWord**, a streaming int8 TFLite model (Apache-2.0), with a custom "Hey CARL" model.
  - **The runtime is our own code,** built from Espressif's `esp-tflite-micro` and TensorFlow's audio microfrontend. No ESPHome code is copied.
  - **Fallback if Phase 0 fails:** Espressif WakeNet with a ready-made phrase.
- **Training:** the user runs it in Google Colab, on a free T4 GPU.
  - **Risk:** Colab moved to Python 3.13, and community reports (November 2026) say `piper-phonemize` has no 3.13 wheels, which breaks sample generation.
  - **Fallback:** train on this PC in a separate folder (`tools/wakeword/`, its own uv project with Python 3.10). It's never part of the server's dependencies, and it's slower because it runs on the CPU.
- **Licence note:** the notebook's augmentation datasets have mixed licences, so a model trained with them is for **personal, non-commercial use**. That's fine for CARL. Revisit before distributing anything, as with Piper.
- **Privacy:** no audio leaves the robot until the phrase is heard or the key is pressed.

## What the model expects (from microWakeWord's training code)

- **Audio:** 16 kHz, mono, 16-bit.
- **Features:** the microfrontend with a 30 ms window and a 10 ms step, 40 channels, a 125–7500 Hz band, PCAN on, `min_signal_remaining` 0.05, and uint16 output. The noise-reduction defaults come from TFLM. The training code's parameters are the source of truth: any mismatch silently ruins accuracy, so Phase 0 checks this. It feeds the same WAV through our C frontend and through `pymicro_features`/TF on the PC, and compares the features.
- **The manifest** (written by hand, ESPHome v2 format, kept as `firmware/models/hey_carl.json`):
  - `wake_word`;
  - `model`;
  - `micro.probability_cutoff` (a 0–1 float);
  - `micro.sliding_window_size` (probabilities are averaged over this many steps);
  - `micro.feature_step_size` (10);
  - `micro.tensor_arena_size` (bytes).

  The cutoff and window size are tuned in Phase 0.

## Phase 1: the full feature (detailed into tasks after Phase 0 passes)

**Robot (firmware)**
- **When it listens:** detection runs only while the state is `idle` (sleeping). It pauses during listening, thinking and speaking, and ignores triggers for 2 s after any state change.
- **On a detection:**
  - the eyes open at once;
  - it sends `wake {score}` (already reserved in `docs/protocol.md`; document it fully);
  - it keeps a 1.5 s PSRAM pre-roll and, once the server says `listening`, streams the audio from just after the phrase first.
- **Settings:** `wake on|off` and `wake threshold` in NVS through the serial menu. The server can set both after `welcome` (a new `wake_config` message).

**Server**
- **End of speech:**
  - Silero VAD in streaming mode (the model faster-whisper already ships, onnxruntime), on the robot's mic stream;
  - the question ends after `WAKE_END_SILENCE` = 0.8 s of silence following speech;
  - no speech within 4 s means a false wake (back to idle, logged, an event);
  - a question is cut off at 15 s at most.
- **The follow-up window:** after a reply to a wake-started question, CARL listens for `FOLLOW_UP_SECONDS` = 5 (0 turns it off). It starts 0.5 s after the audio ends, and silence returns it to idle. The eyes show a softer "listening" look.
- **The key:** push-to-talk always overrides.
- **Without a robot:** the PC alone stays push-to-talk only.
- **Dashboard:** a "Wake word" settings group (`WAKE_WORD`, `WAKE_THRESHOLD` sent to the robot at once, `FOLLOW_UP_SECONDS`, `WAKE_END_SILENCE`). The Live tab shows wake (score), false wake, and follow-up start and end.
- **Tests:** endpointing with recorded and synthetic audio, false wake, the 15 s cap, follow-up timing, the key overriding, and the fake robot sending `wake` from start to finish.
- **Docs:** `docs/protocol.md`, `docs/wiring.md` (if anything changes), `CLAUDE.md` (stack, protocol, roadmap: the wake word moves out of "Later"), `decisions.md`, `status.md`, and both READMEs.

## User check (after Phase 1)

1. Say "Hey CARL, what's the time?" from across the desk. The eyes open, and CARL answers.
2. Follow up within 5 s without the phrase. It answers. Stay silent and it goes back to sleep.
3. "Hey CARL, open that page" after a search, then just "yes" in the follow-up window. It opens.
4. Let the TV run for an evening and count false wakes on the Live tab.
5. The key still works, and interrupts a reply.
