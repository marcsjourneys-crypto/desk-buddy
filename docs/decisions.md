# Decisions

A running log of project decisions. Newest last. When a decision changes, add a new entry (don't rewrite history) and update `CLAUDE.md` in the same commit.

Format: **Decision** — why · alternatives considered.

## 2026-11-23

- **Server targets Windows, not macOS.** The server runs on a Windows 11 PC (current dev machine: i7-1355U laptop, 16 GB RAM, no discrete GPU), so everything must run well on CPU; CUDA is optional. · Alternatives: Mac Mini M4 Pro (original brief).
- **STT: faster-whisper, int8 on CPU, starting with `base.en`.** Fast on CPU via CTranslate2; model, device and compute type configurable. · Alternatives: mlx-whisper (Apple Silicon only), openai-whisper (much slower on CPU).
- **TTS: Windows SAPI voices first, then Piper as the default.** SAPI needs zero setup; Piper is local and runs on Windows. · Alternatives: macOS `say` (Mac only).
- **Computer control (M7) uses Windows mechanisms.** Spotify Web API, Win32 `SendInput` media keys, apps launched by full exe path. · Alternatives: AppleScript / Apple Shortcuts (Mac only).
- **src layout with a single `desk_buddy` package** (`server/src/desk_buddy/`). One import name avoids clashes with generic names like `audio` or `tools`, and tests can't pass against uninstalled files. · Alternatives: flat top-level packages (`server/brain/`), single package without `src/`.
- **uv installed via winget.** Standard Windows package manager; independent of the system Python. · Alternatives: astral.sh PowerShell installer, `pip install uv`.
- **ruff for lint and format; no type checker yet.** One fast dev-only tool. · Alternatives: ruff + mypy now (audio libraries have patchy type stubs, so it would be noisy early).
- **Code review: `python-reviewer` agent adapted from everything-claude-code (MIT), plus `/code-review`.** Gets a focused Python checklist plus Desk Buddy safety checks without the whole ECC plugin's many auto-triggering agents and hooks. Attribution in `THIRD_PARTY_NOTICES.md`. · Alternatives: install the full ECC plugin.
- **Text files stored with LF** (`.gitattributes`). · Alternatives: let Git use CRLF per platform.
- **Use uv-managed Python only** (`python-preference = "only-managed"` in `server/pyproject.toml`). The venv had been built on the Microsoft Store Python, whose app package has no microphone capability: every mic failed on MME, DirectSound and WASAPI, while uv's standalone CPython opens them all. · Alternatives: WDM-KS capture (exclusive, native rates only, skips Windows mic processing); a python.org install.

## 2026-11-23 — M1 voice loop

- **Audio I/O: sounddevice confirmed.** The mic input stream stays open and only buffers while the key is held. One long-lived output stream plays sentences without gaps. · Alternatives: PyAudio.
- **SAPI via comtypes on a dedicated COM thread.** It renders to an in-memory 16 kHz stream with `SVSFIsNotXML`. · Alternatives: PowerShell subprocess, pywin32, pyttsx3.
- **VAD: faster-whisper's bundled Silero ONNX (`vad_filter=True`).** No PyTorch. · Alternatives: silero-vad package.
- **Push-to-talk: a global hold key via `GetAsyncKeyState` (ctypes).** `PTT_KEY` defaults to Right Ctrl. · Alternatives: Enter toggle, tap + VAD end.
- **Interrupts: pressing the key mid-turn cancels the turn task and stops playback.**
- **LLM effort `low` by default (`LLM_EFFORT`)** for latency on Haiku 5.5. Measured on the i7-1355U laptop, counted from key release, for a 5 s question: STT 666 ms, first token 1245 ms, first audio 1815 ms. · Alternatives: default `medium`.
- **Whisper `beam_size=1`** (greedy) for CPU latency.
- **LLM provider seam: `LLM_PROVIDER` (only `anthropic` for now) + `llm.create_chat()`.** The loop depends only on `stream_reply()`. OpenAI-compatible providers (Kimi, OpenRouter, Ollama) are planned after M3, once tool calling is settled. · Alternatives: Kimi support in M1; no seam.
- **New `.env` keys:** `LLM_PROVIDER`, `LLM_EFFORT` (default `low`), `PTT_KEY` (default `right_ctrl`).
- **`anthropic` SDK 2.x uses `httpx2`**, not `httpx`.
- **Async tests use `asyncio.run`**, so no pytest-asyncio.

## 2026-11-23 — M2 personality

- **Character: cheerful and calm, with the odd dry, witty line.** It's one prompt in `brain/personality.py`. The name is still TBD (currently Buddy).
- **Emotion tags are read by a streaming parser** (`brain/emotion.py`). A missing or unknown tag means neutral, and known tags later in the reply are removed so they aren't spoken. · Alternatives: structured output, a separate classification call.
- **Memory lasts until restart, capped at `HISTORY_TURNS` exchanges (default 20).** · Alternatives: forget after a period of idle time.
- **Only what was heard is remembered.**
  - A sentence counts once it starts playing.
  - Failed turns, and turns interrupted before any speech, are dropped.
- **Interruptions are noted on the user's next message, not in Buddy's stored reply.** In the first live test, Claude copied an "(interrupted)" marker from its own stored reply into a new reply, and the voice spoke it. · Alternatives: a marker at the end of the stored reply (the original design).
- **Forget command: fixed phrases checked in code** ("new topic", "forget that", "start over"…, in `brain/memory.py`). · Alternatives: a Claude tool.
- **Short replies are enforced by the prompt only** (`MAX_SENTENCES`, about thirty words), so "tell me three facts" still works.

## 2026-11-23 — M3 design and roadmap

- **Buddy gets an Obsidian vault of its own.** Daily notes go in `Daily/YYYY-MM-DD.md` and ideas in `Ideas/YYYY-MM-DD <title>.md`. Buddy only appends and creates; it never edits or deletes. · Alternatives: write into the user's main vault, match an existing daily-notes plugin.
- **Dictated notes are lightly cleaned by Claude**: mishearings, punctuation and filler are fixed, and Buddy confirms briefly. · Alternatives: verbatim, summarised.
- **Tools run in our own streaming loop inside `ClaudeChat`**, up to 3 rounds, with `tool_choice: none` on the last round and strict schemas. · Alternatives: the SDK's beta tool runner; catching note phrases in code without Claude.
- **Planned browser UI.** M8 grows to cover settings (the vault path and other non-secret settings move to a UI-editable file; secrets stay in `.env`) and personality editing. A new M9 adds an eye-expression library after M6. This makes FastAPI the likely M4 choice.

## 2026-11-23 — M3 Obsidian dictation

- **The vault boundary is checked lexically** (`os.path.abspath` plus `is_relative_to`), not with `Path.resolve()`. On Windows, `resolve()` sometimes returned `\\?\` paths depending on timing, so the check failed at random. Buddy only writes paths it builds itself, and file names are sanitised by `safe_title`. · Alternatives: `resolve()` (follows symlinks, but flaky here).
- **Folder settings are validated with `PureWindowsPath`.** A drive, a root or `..` is rejected, including drive-relative paths like `C:x`. A plain string check let `C:x` through.
- **Logs show only an 80-character preview of each tool result.** That's enough to see that a note was saved without copying everything you dictate into the console log.
- **Running out of tokens before any text plays the error line.** A tool round can use up `MAX_TOKENS` before Buddy says anything, and silence would be confusing.
- **To do before M7:** text that `read_notes` returns comes from files, not from the user. Before computer-control tools exist, it must be marked as untrusted so a planted note can't steer Buddy (prompt injection).
- **Known minor issue:** in the voice check, Buddy repeated the prompt's example confirmation ("Noted: pick up dog food.") word for word. Harmless; vary the example if it becomes repetitive.
- **Voice check passed (user):** a daily note, an idea file whose misheard title was cleaned up, and a read-back summary. First audio took 2.5–3.8 s with a tool round, against about 1.8 s without one.

## 2026-11-24 — M4 robot link

- **FastAPI and uvicorn, in the same asyncio loop as the voice loop.** One process; Ctrl+C stops both. uvicorn's own signal handling is turned off, and the socket is bound first so a busy port is a clear startup error. FastAPI will also host the M8 dashboard and M9 expression library. · Alternatives: the plain `websockets` library; a separate server process.
- **The robot takes over the devices.** While a robot is connected, its mic, speaker and button are used and the PC key is ignored. `DeviceSwitch` sits behind the orchestrator's existing `Mic` and `Player` interfaces, so the core loop only gained a `reset` event. · Alternatives: PC and robot both active.
- **The newest authenticated connection replaces the old one (close code `4003`).** A dead Wi-Fi socket can linger for up to 40 s before pings catch it; refusing the reconnect would leave the robot deaf for that long. · Alternatives: refuse while one is connected.
- **Localhost by default** (`SERVER_HOST=127.0.0.1`, `SERVER_PORT=8765`). LAN binding and the Private-only firewall rule are documented in `docs/protocol.md` and switched on in M6.
- **`ROBOT_TOKEN` of at least 16 characters; blank turns the link off.** Compared with `hmac.compare_digest` on bytes and never logged (the hello message's repr masks it). A token that isn't valid UTF-8 closes with `4002`, not a server error.
- **Speech to the robot is paced at real time with about 200 ms of lead.** It keeps "only what was heard is remembered" accurate, keeps the robot's buffer small and lets `audio_stop` take effect quickly. Known: up to ~200 ms of already-queued audio can arrive after `audio_stop`, so the robot drops audio until the next `audio_start`.
- **Robot mic recording follows the button, not the orchestrator.** The link starts and ends the clip on `button down`/`up`, so a fast re-press can't lose the start of the next clip.
- **Tests run a real uvicorn server on a loopback port** with the fake robot client, instead of FastAPI's `TestClient`. That exercises the real socket, ping and close-code paths, and avoids adding `httpx`. · Alternatives: `TestClient` (needs `httpx`).
- **The fake robot is a test helper and a voice tool** (`python -m desk_buddy.fake_robot`), so the link can be voice-checked before the hardware works.
- **`wake {}` is reserved** for an on-robot wake word ("Later" on the roadmap). The server accepts and ignores it.
- **Deferred to M6** (when the server listens on the LAN): throttling failed auth attempts, a cap on open connections, limits on button floods, and bounded send queues.
- **Voice check passed (user):** a question, an interrupt mid-reply and a disconnect through the fake robot. The follow-up after the interrupt didn't mention it (the M2 fix, now checked). Not checked by hand: Right Ctrl after the robot disconnects (covered by tests).

## 2026-11-24 — M5 firmware bring-up

- **Arduino core 3.x via pioarduino, pinned to `55.03.312-1` (core 3.3.12, ESP-IDF 5.5.5),** on the ready-made `esp32-s3-devkitc1-n16r8` board definition (16 MB flash, octal PSRAM). Core 4.0 was days old; the official PlatformIO platform is frozen at core 2.x with the legacy I2S driver. · Alternatives: core 2.x on the official platform.
- **Windows setup it needed:** PlatformIO Core 6.2 via `pioarduino==6.2.0` (PlatformIO's semver check reads `.post1` as a pre-release), installed while PlatformIO isn't running; long paths turned on; `pio` run from PowerShell only. Written up in `firmware/README.md`.
- **LovyanGFX 1.2.36 for the eyes.** It has anti-aliased circles and `drawWedgeLine`, but no smooth arc, so curves are drawn as thick wedge segments. · Alternatives: TFT_eSPI (core-3.x/S3 issues), Arduino_GFX (no anti-aliasing).
- **The eye model is two lid bulge values plus size, thickness and gaze.** A ring, `∩`, `‿` and a closed line all come from it, and every blend is a plain lerp. M9's editor can store the same numbers. · Alternatives: bitmaps per expression.
- **One 200×200 sprite in internal RAM, drawn once and pushed to both eyes when they match, redrawn only while something moves.** Measured: 10.9 fps with two 240×240 PSRAM sprites, 25.7 fps now; 16 segments per curve (24 gives 22 fps; the user found 16 smooth). The wedge-line drawing is the cost, not PSRAM. Free heap with everything running: 229 KB.
- **One app with a serial test menu,** and the pure logic in header-only files tested with Unity on the board (no C++ compiler on the PC). 28 tests.
- **The PSRAM strip-drawing fallback was dropped:** PSRAM is confirmed (8 MB octal).
- **Audio:** speaker on I2S port 0 with mono data on both slots; mic on port 1 (INMP441, 24-bit in 32-bit slots, left). The mic gets +12 dB (`kMicShift = 14`); speech peaked near −4 dBFS close up, so this may come down. The idle level read −28 to −38 dBFS, probably room noise plus the INMP441's DC offset; M6 should remove DC before streaming. Stale DMA audio is flushed before each recording. Volume starts at 20.
- **The board's 5V pin gives no USB power** (the IN-OUT jumper is open), so the amp runs on 3.3 V for now; the 5 V 3 A supply will feed the amp and servos in the final wiring. Don't bridge IN-OUT while an external 5 V supply can be connected.
- **Servos: attached once, eased at 90 °/s, and stopped with duty 0 after a 200 ms settle** instead of detaching the pin, which could cut a pulse short and twitch the servo. Pan ±60°, tilt ±20° (provisional). The first move after power-on jumps to centre.
- **Hardware checks passed (user):** LED and PSRAM, both eyes (expressions, blink, smoothness), the tone and volume, mic levels and the record/playback loopback. **Pending:** the servo sweep, once the servos are wired to the 5 V supply.

## 2026-11-24 — M6 robot joins the link

- **The talk button is the PC key (Right Ctrl) for now,** held in the Buddy window. The robot has no button or touch pad wired yet. While a robot is connected, the key opens and closes the robot's mic recording instead of being ignored (this reverses the M4 "PC key is ignored" rule). A robot button, touch pad or wake word can send the existing `button` message later. · Alternatives: wire a button first.
- **The robot's mic stays open 250 ms after the key is released** (`RELEASE_DELAY`), so frames still in flight over Wi-Fi arrive before the turn starts. A re-press inside those 250 ms ends the first clip at once; it is then too short and is dropped as a tap, by design.
- **The robot streams its mic exactly while the server's state is `listening`.** No new protocol message; the server stays the source of truth. The firmware flushes stale DMA audio, then removes the mic's DC offset with a one-pole high-pass filter (r = 0.995, seeded with the first sample so the offset doesn't thump).
- **Robot settings are typed once over serial and kept in NVS** (`wifi`, `server`, `token`, `config` masked, `forget`, plus `net` for status). They survive reflashing and nothing secret goes into the build. · Alternatives: a gitignored `secrets.h` (a rebuild per change); a captive portal (more code and a library).
- **Two firmware libraries, pinned:** `links2004/WebSockets@2.7.3` (core 3.3 has no WebSocket client) and `bblanchon/ArduinoJson@7.4.3` (the JSON control messages, with correct escaping in `hello`). The server gained no dependencies.
- **The library doesn't expose close codes.** In WebSockets 2.7.3 the code of a received close is parsed only for a debug log, and the app gets the same `WStype_DISCONNECTED` for every close. So the firmware treats a close less than 1 s after `hello` as a refusal; three in a row stop the retries (`Server refused the robot … check: token <value>`), with a retry every 5 minutes and at once after a settings change. A missing `welcome` (5 s) is an ordinary failure. The library's own auto-reconnect is disabled so the firmware's back-off (1 s doubling to 30 s) drives every attempt. · Alternatives: patch the library.
- **Robot audio threading:** the mic task and the playback task run on core 1; the WebSocket and the eyes run in the main loop. Speech is buffered in a 1 s PSRAM ring and each sentence starts after ~60 ms is buffered; `audio_stop` clears it and fades out the block in hand. Mic frames reach the main loop through an 8-deep queue. The serial audio tests (and `servo`, `fps`) are refused while the link is connected.
- **Speech to the robot goes in 100 ms frames (3200 bytes), not 20 ms.** The ESP32's lwIP queues at most 6 received segments per socket (`CONFIG_LWIP_TCP_RECVMBOX_SIZE`; window 5760 bytes; 250 ms TCP timer), so one small segment per 640-byte frame capped the robot at ~31 frames/s, below real time, and after ~7 s of speech the server's send queue overflowed and closed the link (`1011`). Full-size segments hit the window first instead. Found in the first voice check. Mic frames up stay 20 ms. · Alternatives: raise the lwIP mailbox size (needs a custom ESP-IDF build).
- **The eyes follow state and emotion** (`firmware/include/looks.h`): idle → idle, listening → wide and attentive, thinking → the animated swirl, speaking → the reply's emotion, not connected → sleep. Emotions: neutral → idle, happy → happy, sad → the new tilted `sad` look, surprised → the burst, sleepy → sleep, thinking → skeptical, curious → look up. The eye model gained `tilt`; the lead's eye work added crescent looks, `lookaround`, and animated specials (thinking swirl, surprised burst, `excited` sparkle; the old drifting look-up is `ponder`). Reference images: `docs/looking.png`, `look around.png`, `thinking.png`, `surprised.png`, `excited.png`. The lids are capped at ~30 fps so the main loop has time for the link.
- **Hardening for the LAN** (in memory, constants in `server.py` and `link/robot.py`): 5 bad tokens from one IP within 60 s block it for 60 s (timeouts and bad hellos count; blocked IPs get `4001` at once); at most 4 connections waiting for a hello, 2 per IP (`4002`); 10 button downs a second with a burst of 10 (ups are never limited); a send queue of 128 items, which closes with `1011` on overflow; closing a link waits at most 2 s.
- **LAN setup:** `SERVER_HOST=0.0.0.0`, a Private-only firewall rule for TCP 8765 (PowerShell and cmd versions in `docs/protocol.md`), and the startup log prints the PC's LAN IP with the exact `server` command. A DHCP reservation for the PC is recommended. Without the firewall rule, connects to a stopped server time out after ~5 s instead of failing fast (Windows drops rather than refuses), which blocks the robot's main loop for that long.
- **Not in M6:** servos following `look`, the antenna LED and the touch pad, because they aren't wired yet. Their messages stay reserved.
- **Voice check passed (user):** the robot linked over Wi-Fi; a question through the robot's mic was transcribed correctly; the reply played on the robot's speaker; an interrupt worked; reconnecting worked. Stopping the server gracefully or killing it both make the robot print `Disconnected` within ~0.5 s, and the eyes sleep. Measured from key release: STT 1048 ms for 2.9 s of audio, first token 2577 ms, first audio 2969 ms.

## 2026-11-25 — CARL-42 personality

- **The character is renamed Buddy → CARL-42** ("CARL" for short; the Cognitive Assistant Robot for Life). Only the character: the repo, the `desk_buddy` package, the commands and the GitHub repo keep their names. The prompt, canned lines, logs (`CARL [happy]: …`) and docs change. The forget command also accepts "Carl" or "Karl" (Whisper's frequent spelling) as a filler ("Hey Carl, new topic"), alongside "Buddy". · Plan: `docs/plans/2026-11-25-carl-personality.md`.
- **A light *Hitchhiker's Guide* flavour, as an original character.** Calm, helpful and brief, with a dry, cosmic aside roughly one reply in four, never when the user is frustrated or rushed and never more than one per reply. Short homage lines are fine in a personal robot ("Don't panic", 42, the fish); CARL never imitates a character from the books (no Marvin) and never quotes them at length.
- **Signature lines, each with a rule so they stay a treat.** None is remembered, and a key press stops any of them like other speech.
  - `GREETING` "Don't panic. CARL is online.": once at startup (a `greet` event queued after `Ready`), and when a robot connects (the server's `on_connect` hook queues `greet` right after the connect's `reset`), skipped if a greeting finished playing in the last 60 s (`GREET_GAP`; an interrupted or failed one doesn't count) or CARL isn't idle.
  - `FAREWELL` "So long, and thanks for all the fish.": on Ctrl+C, as the last exit-stack callback pushed, so it runs first, before the key watcher, the server and the devices close. It interrupts whatever was happening, is cut off after 5 s (`FAREWELL_TIMEOUT`, with a hard cap of 6 s, `FAREWELL_HARD_CAP`), and any failure is logged and skipped. It replaces the logged "Bye".
  - `PONDERING` "Contemplating life, the universe, and everything.": if no reply sentence is ready 4 s after CARL starts thinking, i.e. after transcription ends (`PONDER_AFTER`; counting from key release would let a long question's STT trigger it), at most once every 5 minutes (`PONDER_EVERY`); the reply plays after it. While the line plays the reply's emotion is held back, then sent when it ends. The "First audio" latency log is for the reply only.
  - A failing `PONDERING` or `TASK_DONE` line is skipped with a warning (`_say_extra`): an extra line must never cost the real reply.
  - `TASK_DONE` "Another mystery of the universe solved.": after a reply whose turn ran at least one successful tool call, with probability 1/4 (`TASK_DONE_CHANCE`), not after a failed reply. `ClaudeChat` keeps a running `tools_succeeded` count; the loop compares it before and after the reply (a chat without the count never triggers it).
  - 42 is prompt guidance only: say plainly when you don't know, and at most once per conversation add that the answer might be 42.
- **`ERROR_LINE`** is now "Sorry, my brain seems to be on the other side of the galaxy right now." Refusal and forget lines are unchanged.
- **The voice is chosen separately** (a Piper audition is next); a British voice may suit CARL.

## 2026-11-25 — CARL's voice (Piper)

- **Piper is the default TTS engine** (`TTS_ENGINE=piper`; the Windows SAPI voice stays as the fallback, `TTS_ENGINE=sapi`). New dependency `piper-tts==1.8.0`, approved by the user. It is **GPL-3.0**: fine for this personal project, but revisit before distributing the server. · Alternatives: keep SAPI (robotic); a cloud voice (latency, cost, a network dependency).
- **CARL's voice is `en_GB-northern_english_male-medium`**, chosen by the user after auditioning 8 Piper voices. Settings: `TTS_VOICE` (a voice name, or a path to an `.onnx` file with its `.onnx.json`), `TTS_SPEED` (0.5–2.0, sent as `length_scale = 1 / speed`) and `VOICES_DIR` (default `%LOCALAPPDATA%\desk-buddy\voices`, outside the repo).
- **A missing voice downloads at startup, atomically** (about 60 MB for a medium voice, logged like the Whisper download). The server fetches both files itself (`urlopen` with a 30 s timeout, reusing Piper's `URL_FORMAT` and name parsing) into a temporary subfolder of `VOICES_DIR`, and moves them into place only once both arrived. A voice with only one of its two files counts as missing and is downloaded again. A voice downloaded just now that fails to load is deleted, so the next run tries again (a voice that was already there, or a custom `.onnx` path, is never deleted). Any failure stops startup with a clear error that suggests `TTS_ENGINE=sapi`.
- **Voice names are strict ASCII** (`[A-Za-z]+_[A-Za-z]+-[A-Za-z0-9_]+-[A-Za-z0-9_]+`, full match), so a name can never be a path (`/`, `\`, `..`). `TTS_VOICE` and `TTS_SPEED` are checked only when `TTS_ENGINE=piper`, so `TTS_ENGINE=sapi` always works as the fallback.
- **Resampling to 16 kHz in numpy** (no new dependency): Piper renders at 22050 Hz, and everything downstream (the loop, the PC speaker, the robot) expects 16 kHz. `tts.resample` is a windowed-sinc (Blackman, 96 taps) low-pass interpolator at 7.4 kHz: flat to 7 kHz (−0.2 dB), −6 dB at 7.4 kHz, below −80 dB from 8 kHz, so nothing aliases. The 320 filter phases for 22050 → 16000 are computed once and cached; that made resampling ~10× faster (from 250–520 ms to 20–45 ms per sentence). · Alternatives: linear interpolation (aliasing); `scipy`/`soxr` (a new dependency).
- **Threading:** `PiperSynthesizer.synthesize` is blocking and serialised with a lock, so two renders never overlap; the loop already runs it in a worker thread, as it did for SAPI. Text goes to Piper as plain text (no markup parsing).
- **Speed** (i7-1355U, measured outside the app, warm): 90–210 ms per typical sentence including resampling, about 20× real time (the audition measured 14–24×). SAPI took 16–20 ms, so first audio comes roughly 0.1–0.2 s later than with SAPI. The first sentence after startup also pays onnxruntime's warm-up.

## 2026-11-25 — M7 Spotify control

Plan: `docs/plans/2026-11-25-m7-spotify.md`. M7 covers Spotify only; media keys, apps, websites and PC volume come later.

- **Spotify through its Web API with `spotipy==2.26.0` (MIT)**, approved by the user (it brings `requests`, and `redis`, unused). The user has Premium, which remote playback control needs. Login is PKCE (no client secret): `python -m desk_buddy.spotify_login` opens the browser with redirect `http://127.0.0.1:8888/callback` and saves the token to `%LOCALAPPDATA%\desk-buddy\spotify_token.json`. Scopes: playback state and control, currently playing, private playlists.
- **spotipy pitfalls, handled:** it logs request headers (the bearer token) and token-refresh bodies (the refresh token) at DEBUG, so the `spotipy` logger is held at WARNING. With no usable cached token (or new scopes) its auth manager starts an interactive login (a browser or `input()`), which would hang the server, so the server's PKCE subclass refuses and CARL says "run the Spotify login". Its PKCE token calls have no timeout by default; ours use 10 s.
- **Off by default, then gated in code** (`tools/actions.py`, `ActionGuard`): `COMPUTER_CONTROL=on`, plus `SPOTIFY_CLIENT_ID` and a saved login, or the music tools aren't registered and the prompt says music isn't set up. At most 3 actions per question and 8 per rolling minute (an attempt counts even if it fails; a refusal doesn't); every attempt is logged as `Action: <tool> <args> -> <result>`. The loop calls `guard.new_question()` at the start of each turn.
- **Model text never builds a command:** `query` is only a parameter to Spotify's search; `kind` and `action` are enums; playback uses the URI Spotify returned. If no device is usable, CARL starts the app with the fixed `os.startfile("spotify:")` and waits up to 12 s (see below), then makes that device active without starting music (`force_play=False`).
- **Device choice:** devices without an id, or restricted ones, are ignored. Then this PC's Spotify (a Computer device named like the PC), else any computer running Spotify (its Spotify name can differ from the PC's), else the active device, else start Spotify here. So an active phone never steals playback when the PC's Spotify is open. A just-started device can 404 on transfer for a moment, so the transfer is tried 3 times ("Spotify isn't ready yet" if it still fails).
- **Bounded calls (review):** every spotipy call runs in a worker thread with a 12 s deadline (`CALL_DEADLINE_S`), 5 s per request, one connection retry, and no status retries, so urllib3 never sleeps for a long `Retry-After`; a 429 says "Spotify is busy, try again in a moment". A 400 or a 403 other than `PREMIUM_REQUIRED` says "Spotify said no to that" rather than blaming the network. Action log lines cap the arguments at 200 characters.
- **Playlists:** the user's playlists first, the ones they made and the ones they follow (Spotify lists both as "your playlists"; up to 200), then public search. Filler like "my … playlist" is dropped, then: an exact name, else a whole-word part of at least 3 characters that is at least half of the longer name, else a fuzzy match ≥ 0.6. So short names like "Mix" or "Love" don't capture "a jazz mix" or "love songs".
- **Untrusted text:** results with outside text (`read_notes`, Spotify names) are wrapped in `<untrusted source="…">` by `tools/untrusted.py`, which escapes every `&`, `<` and `>` inside (sturdier than looking for the tag) and applies any length cap after escaping; the system prompt says it's data, never instructions, and never authorises or confirms an action.
- **`music_volume` takes exactly one of `level` (0–100) or `change` (−50..50)**, as nullable integers in a strict schema; the ranges are checked in code.
- **Ducking (`MUSIC_DUCK`, on by default):** driven by the orchestrator's state, so every way a turn ends (reply, interrupt, error, reset, farewell) restores the music. It runs on its own worker thread with its own Spotify client (2 s timeout, no retries), so listening is never delayed and a failure is only a warning; a failed restore is retried after the next turn. Closing the ducker at shutdown always restores, even mid-turn or after a farewell that timed out. The pre-duck level is recorded before the duck call, so a duck that lands but times out is still restored (only a definite "no" from Spotify drops it). A tool that starts or resumes music mid-turn re-ducks it under the reply. A volume the user sets while ducked counts from the pre-duck level, never interleaves with a duck in flight (the user's level wins), and cancels the restore only once it has been set.
- **No spoken "yes" for music:** it isn't powerful. The confirmation mechanism comes with the first powerful tool.
- **Integration test:** a real search only (no playback), skipped without a saved login.
- **Memory keeps tool calls (found in the voice check).** Memory used to keep only the user's words and the spoken reply, so on the next turn Claude saw "Queen is playing" with no call behind it and apologised that it never started Queen. Now each turn also keeps its tool rounds as real API blocks (an assistant message of `tool_use` blocks, then a user message of their `tool_result` blocks), before the reply. The spoken text of a tool round is folded into the final reply (it was heard), and thinking blocks are dropped (only the current tool loop needs them). Results are capped at 300 characters, cutting inside an untrusted block so it stays well formed. Tools that ran are kept even if the reply was cut off or failed. A tool cut off mid-run (or never reached in a multi-tool round) is recorded with the result "Interrupted; the action may have completed.", so every `tool_use` keeps a result and the action isn't forgotten. Every stored turn ends with its spoken reply (review): a turn with tools but no reply isn't stored as blocks (a turn ending on tool results is risky with thinking enabled, and made-up assistant text gets copied, as M2 showed). Instead the next user message starts with "(I cut you off before you replied, after you ran: …)", listing each call and its result compactly (untrusted blocks kept well formed), and the system prompt explains it. Turns are kept or dropped whole, so trimming never orphans a `tool_use`. Prefixed results ("Started playing on Spotify: <untrusted …>") are cut inside the block too.
- **Spotify start-up is bounded (found in the voice check).** With Spotify closed, "play …" logged `Starting Spotify` and then nothing for 37 s until the user interrupted. Every API call was already capped at 12 s and logs when it gives up, and none did, so the one unbounded step was `os.startfile("spotify:")` itself, a ShellExecute that can block while Windows launches the app, run straight in the tool thread. Now the launch runs on its own daemon thread (waited on for at most 1 s, only to catch an immediate failure); the device is polled with 3 s calls for up to 12 s (the desktop app registers its device only once its UI has loaded, ~5–10 s on this laptop); and `play_music` and resume run under one 15 s deadline overall, which every call inside is clamped to, so a slow start says "Spotify didn't open" (or "Spotify isn't ready yet" if the transfer is what runs out of time). An interrupt never waits for any of it: the tool runs in a worker thread that the cancelled turn stops awaiting.

## 2026-11-25 — M8 dashboard

Plan: `docs/plans/2026-11-25-m8-dashboard.md`.

- **This PC only:** a second listener on `127.0.0.1:8766` (`DASHBOARD_PORT`) in CARL's own process and event loop, with the M4 `start_server` pattern; the robot keeps its LAN port. No password, because nothing off this PC can connect. A busy port logs `Dashboard: off (…)` and CARL runs without it.
- **No build step, no new dependencies:** plain HTML, CSS and JS in `src/desk_buddy/dashboard_static`, served by FastAPI from a fixed list of files. Nothing from a CDN.
- **Security in depth for a localhost page** (a web page in the user's own browser is the threat):
  - every request must carry our `Host` (`127.0.0.1:<port>` or `localhost:<port>`). This wasn't in the plan; it was added because Origin and token checks alone don't stop DNS rebinding from *reading* the settings;
  - every change must carry our `Origin` and `X-CARL-Token`, a random per-process token put into the served page; refused changes are drained first so the socket closes cleanly;
  - the event WebSocket must carry our `Origin` (refused before accept: the browser sees a 403);
  - a strict Content-Security-Policy (nothing inline, nothing from elsewhere, no framing), `nosniff`, `no-referrer`, `no-store`, and a 64 KB body limit;
  - text from CARL's world is sent as JSON strings and rendered only with `textContent` (checked by a test on the page source);
  - no secret ever goes out: the settings view only has editable keys, the status only says whether things are on. Tests plant secret values and search every response and event for them.
- **Live events:** `events.EventBus`, called from the loop, the action guard (from tool threads, via `call_soon_threadsafe`) and the robot server. It never blocks or raises; each page has a bounded queue (a slow page loses events); the newest 100 are kept in memory only, and a page that connects gets them first (events carry an id so nothing is shown twice). Events: state, emotion, heard (with STT time), reply (what was actually said, with first-token and first-audio times), line, action (args and result bounded, outcome ok, failed or refused), robot, interrupted.
- **Settings precedence: dashboard over `.env` (and the process environment) over defaults**, in `%LOCALAPPDATA%\desk-buddy\settings.json`. Only `config.DASHBOARD_KEYS` can come from the dashboard; a blank value means the default. Validation is `config.py`'s own (each change is checked by loading the settings with it; all or nothing). Saves are atomic (a temp file, then `os.replace`). Only the real startup reads the file, so tests and tools never see the user's settings; a saved value that no longer validates (a deleted vault folder) is skipped with a warning at startup, never fatal.
- **Live apply:** `LiveSettings` holds the running settings. A change is proposed at once (TTS speed is set on Piper immediately: the next sentence) and applied when the next turn starts. Then the `Brain` in `__main__` sets the guard switch, rebuilds the music tools and ducker if computer control or ducking changed (an old ducker is closed off the loop, restoring the music), and rebuilds the tools and chat for the vault, model, effort or sentence limit; the conversation trims to the new history size. Speech recognition, the key and the voice apply after a restart.
- **Personality file:** `%LOCALAPPDATA%\desk-buddy\personality.json` holds only the character paragraph (at most 3000 characters, no `{`/`}`, not empty) and the seven canned lines (each at most 200 characters, one line, an emotion from the tags). Missing items fall back to the code's defaults; bad items in the file are skipped with a banner. The prompt is the character joined to the locked rules, never formatted. The chat rebuilds the prompt for every request and the loop reads lines when it speaks them, so edits apply at the next question and the greeting and farewell when spoken. The page shows the full assembled prompt as a read-only preview.
- **Tests never touch the user's app data:** `test_main` points `LOCALAPPDATA` at a temp folder.
- **Local trust model:**
  - **What the dashboard stops:** web pages in the user's browser (Host, Origin and token checks).
  - **What it doesn't:** other programs running as the user on this PC. They can read the token from the served page, or the settings files, and the user's account already has full control of this PC anyway. That's the boundary we accept for a personal desk robot.
  - **Never exposed:** secrets never go to the page at all, so even a local reader of the page learns nothing it couldn't read from `.env` itself.
- **Review fixes (same day):**
  - **The ducker is never replaced.** The music tools and ducker are made once, the first time computer control is on with a Spotify login, and kept. MUSIC_DUCK and computer control just switch the ducker (`set_enabled`). Off restores through the ducker's own worker, so it can't race a duck in flight; on is primed with CARL's current state. This fixes a handover that could save a ducked level as the "original" and leave the music low.
  - **Making them later** (computer control turned on from the page) reads the Spotify login on a worker thread; the tools join at the next question.
  - **Turning computer control off applies at once** (an `on_now` hook disables the guard and the ducker), and the status shows it. Turning it on waits for the next question.
  - **A saved value that no longer validates never blocks other edits.** Edits are checked against the good saved values only; the bad one stays in the file, shown as `source: "invalid"` with its error, until fixed or reset. Save failures come back as JSON errors (400 or 503), never a 500.
  - **Startup can't be broken from the page:**
    - `STT_COMPUTE_TYPE` is allowlisted (`default int8 int8_float16 int16 float16 float32`), `STT_MODEL` must look like a model name or repo id (no `..`), and `LLM_MODEL` like a model id;
    - `MAX_SENTENCES` is 1–10 and `HISTORY_TURNS` 1–50;
    - the vault can't be a drive root or the home folder;
    - if Whisper or the Piper voice still won't load with the dashboard's values, startup logs a warning and tries once more with `.env` and defaults for those keys.
  - **Hardening:**
    - Content-Length is parsed safely;
    - the body is capped as it streams (a chunked body can't get past 64 KB);
    - the event socket's pending `queue.get()` is always cancelled;
    - the Brain builds its tools and chat into locals and swaps them in together.

## 2026-11-25 — Web search and About you

Plan: `docs/plans/2026-11-25-web-search-about-you.md`.

- **About you lives with the personality,** in `personality.json` under `about`, edited on the Personality tab with a reset per field. Every field is optional; with all of them blank the prompt is unchanged. The block goes after the character paragraph and before the locked rules, joined, never formatted.

  - **One-line fields** also refuse U+0085, U+2028, U+2029 and the bidi controls (U+202A–U+202E, U+2066–U+2069), so they can't break the prompt's layout or flip the page's text direction.

- **Web search is Anthropic's server tool** (`web_search_20250305`, which works on Haiku 5.5), on by default (`WEB_SEARCH`), at most `WEB_SEARCH_MAX` (1–5, default 2) searches per request. It only reads and runs on Anthropic's side, so it is outside `ToolRegistry` and `ActionGuard` and not tied to `COMPUTER_CONTROL`. Web fetch and the `_20260209` versions are left out.
  - **Location:** `user_location` (`approximate`) gets whichever of city, region and country are filled in, read for every request; with none, the key is left out.
- **The chat loop:**
  - **Sentence breaks:** a `"\n"` goes before text that follows a new round or a non-text block (search, result, tool call, thinking). Text blocks that follow each other get none: a cited answer arrives as several text blocks split mid-sentence, and a break would cut its sentences into fragments (found in review). Citations are ignored.
  - **`pause_turn`:** the assistant content goes back as is, with no extra user message; it uses up one of the 3 rounds, so it can't loop. Back-to-back assistant messages (a pause, then a tool round) are merged into one.
  - **When a search is reported:** as soon as its `web_search_tool_result` block starts streaming (it arrives whole; the query comes from the `server_tool_use` block's stop event, which carries the parsed input), de-duplicated by id and checked again in the final message. So a reply interrupted after a search still shows it, logs it and remembers it (found in review).
- **What the user sees:** each search is an `action` event on the Live tab (`tool: "web_search"`, the query as JSON args, ok or failed, and up to 3 source titles with their sites as plain text, never links; line breaks and bidi controls become spaces), plus an `Action: web_search {"query": …} -> ok (N results)` or `-> failed: <code>` log line. The event goes through the same `publish_action` helper as the guard's, and a failing bus never reaches the turn.
- **`TASK_DONE` ignores searches:** they will be common, and the line should stay a treat tied to our own tools.
- **Memory:** search blocks and results are never stored. A turn that searched gets `(System note: to answer this, you ran web searches for: "q1"; "q2")` after its stored user message. It goes on the user side because Claude copies markers from its own stored replies, and it is labelled a system note because the queries are model-written (and web text may have steered them), not the user's words. Queries are capped at 100 characters, double quotes become single and parentheses become spaces, so a query can't close its quote or the note. A turn with no reply isn't stored, and its searches are dropped (they only read).
- **Search turned off for the account:** a 400 that names web search and says it is not enabled, not available or disabled logs a hint once, retries that round without search and keeps search off until the restart. The flag is module-level in `llm.py` (`web_search_blocked()`), so it survives the chat being rebuilt between turns, and `prompt_for` reads it, so the prompt (and the dashboard preview) says search is off from the retry on. Any other 400 naming web search (a validation error, say) logs the API's own message on one line, retries that round once without search, and leaves search on: a narrow match keeps one odd error from turning search off for the whole session (found in review).
- **Not verified live yet:** the API's exact wording when search is off for an organisation, and whether a resumed last round (sent with `tool_choice: none`) is accepted. The integration test (`tests/integration/test_web_search_live.py`) runs one real search.

## 2026-11-25 — M7 apps and websites

Plan: `docs/plans/2026-11-25-m7-apps-websites.md` (Part 3 revised after review).

- **Apps come from Windows' own list.** `Get-StartApps` covers Start-menu, desktop and Store apps alike, and an app is started as `explorer.exe shell:AppsFolder\<AppID>`, so no exe path or argument from anywhere else is ever run. The listing runs only when the page asks (Find apps), never during a turn; the store keeps the last listing and refuses IDs that weren't in it. The listing endpoint starts PowerShell, so it needs the page's token like a change does.
- **Full paths and UTF-8 (review):** `%SystemRoot%\explorer.exe` and `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, never whatever comes first on PATH. The listing command sets `[Console]::OutputEncoding` to UTF-8 and the output is decoded as UTF-8 only (a BOM is fine), so names in any language come through and nothing is guessed from a code page.
- **Bookmarks and search results share one URL check** (`tools/urls.py` `check_url`): http/https, a host, no user name or password, at most 500 characters, no spaces, control or format characters, no backslash. A page is opened with `os.startfile` on its own thread, waiting at most 2 s for an immediate failure (Windows can block while the browser starts).
- **Rebuilds:** the tools are built from a snapshot of the lists; a saved change bumps a version and the tools and chat are rebuilt at the next question, never mid-turn.
- **Refusals go through the guard (review):** an unknown app or bookmark name, or an address that isn't an exact search result, is refused through `ActionGuard.refuse`: counted toward the limits like any attempt, logged and shown as `refused`. For `open_search_result` the dashboard shows only the site (or "unknown"), never the full address. The music tools still refuse unknown names before the guard; left as is for now.
- **Search result addresses stay on the server.** `llm.py` keeps every result (title, site, full address, not only the 3 shown) in `Search.pages`, which is never on the dashboard; they go into `SearchResults`. It moves along only on a question with speech (an empty clip isn't a question) and a forget command clears it.
- **Last question's pages by number (after the user check).** In real use, "open that page" in the question after a search failed: Claude never sees an earlier question's raw results (memory keeps only the search note), so it had no address, and the "this or the previous question's exact URL" rule was unusable. Now, at the next question with speech, the user's message gets a system note listing the last question's results, numbered. There are at most 10, one per address, in order; titles and sites are cleaned as on the dashboard; the list is wrapped as untrusted (`web_search_results`; a source label can't have spaces). `open_search_result(page)` takes that number, or the exact address of a result from a search in this question (seen raw in the turn). Numbers only mean the latest list, so an old one is refused. `page` is one plain string: the simplest strict-schema shape for "a number or an address". Strict schemas don't support `maxLength` (the SDK's own transform moves it into the description), so the 500-character limit is checked by the server, and the earlier `maxLength` was dropped. The list is stored in memory like the other system notes.
- **Call it, don't offer it (after the user check).** The first prompt said "at most say briefly that you can open it"; CARL then offered ("Just say yes and I'll send it to your browser") without calling the tool, so the "yes" found nothing waiting. The prompt now says to call `open_search_result` straight away when asked, never to ask or tell the user to say yes (the robot asks), and just to say briefly which page it is.
- **No local pages (review):** `open_search_result` also refuses loopback, private, link-local, reserved, multicast and unspecified IP addresses (including IPv4-mapped IPv6 and short numeric forms like `127.1`), `localhost`, `.local`/`.localhost`/`.internal`/`.lan`/`.home.arpa` names and single-label names. A web page can't steer CARL into opening a router or a local admin page. Bookmarks are the user's own choice and aren't limited this way.
- **The spoken yes** (`tools/confirm.py`), the first powerful-action confirmation, built to be reused:
  - **One pending action.** `ActionGuard.run_after_yes` checks and counts the call, then hands it to `Confirmations`; a new one replaces the old (shown as cancelled). The tool result is a `NotDone` string, so it isn't counted as a success (no `TASK_DONE`), and tells Claude not to ask and never to say it's open.
  - **The server asks, never the model (review).** A model could phrase or skip the question, or say "shall I?" about something else. After the reply, the loop speaks the canned line "Shall I open <the page on site>?" (curious, interruptible). The first version armed the action only once that line had played to the end; that changed after the second user check (below). The site comes from a plain host (letters, digits, dots, hyphens); otherwise it is just "the page".
  - **The very next question only (review).** Each question with speech gets a number, set as a context variable in the turn's task; tool threads inherit it, so a late proposal from a cut-off turn is stamped with its own question and can never be asked about or answered by a later one. An armed action is answered only by the next question with speech, within 60 s of the question (not of the proposal, so a long reply doesn't eat the time).
  - **A strict vocabulary (review).** "Yeah, nah", "Okay, never mind" and "Sure, hang on" passed the first version. Now every word must be a yes word or a filler (please, carl, karl, thanks, thank, you, it, go, ahead, do, open, that, alright, right, oh), with at most 6 words, at least one yes word or phrase, and no "no" word. Curly apostrophes are straightened first. A false "no" only costs asking again; a false "yes" opens a page.
  - **On a yes** the action runs once, not counted again, and only if computer control is still on. Claude gets "(System note: the server asked and the user said yes; … was opened.)" after the user's words; cancelled, failed and expired get their own notes. If that turn is never stored (no reply), the note goes in front of the next user message, like the cut-off note (review). Forget and turning computer control off expire it, with no note.
  - **Only the user's voice can confirm.** The check reads the transcript and nothing else: there is no confirm tool, and tests plant "the user said yes" and fake system notes in search result titles and note results.
- **End the turn at the robot's question (second user check).** In real use, after the waiting result the chat made another API round, and Haiku 5.5 asked "Shall I open it in your browser?" itself and repeated itself, despite the prompt. The user cut that off to answer, so the robot's question never played and the action was cancelled; their "Yes." found nothing waiting, and CARL then claimed it was opening the page. Four changes:
  - **No more rounds after a waiting result:** `ClaudeChat` ends the reply as soon as a tool returns `NotDone`. Text already said in that round stands, then the robot asks. The prompt says to call the tool immediately with no text before it (or at most a few words), and never to ask or mention a confirmation.
  - **Armed when the question starts playing,** not when it ends: users cut a question off to answer it. The 60 s count from then. Cutting off CARL's own text before the question still cancels it (the user wasn't asked).
  - **The question is remembered:** it was heard, so the turn's reply in memory is CARL's text plus the question exactly as spoken. The tool round (`tool_use` and the waiting `tool_result`) stays before it, so the next request is assistant `tool_use` → user `tool_result` → assistant text → user (tested). A cut-off question is stored like any interrupted reply.
  - **Claude is always told when nothing happened:** every cancellation or expiry it wasn't told about (cancelled before the user was asked, replaced, dropped by forget or computer control going off) becomes a note on the next user message, delivered once. A bare yes with nothing waiting gets its own note. The prompt says never to claim it's opening or opened anything unless a note says it was opened.
- **Events:** every step is an `action` event (`waiting`, `ok`, `failed`, `cancelled`, `expired`, `refused`) with an `Action:` log line.

- **The microfrontend is vendored** in `firmware/lib/microfrontend` (a PlatformIO library): TFLM removed it upstream on 2026-10-15 and `esp-tflite-micro` 1.4.0 doesn't carry it. Pinned to tflite-micro `5d5a2e9` (its last commit) plus TFLM's KISS FFT from `esp-tflite-micro` v1.4.0; see its README.
- **The model is compiled in** from `firmware/models/hey_carl_model.h`, written by `scripts/model_to_header.py` from the `.tflite` and the manifest (stdlib only). Without it the firmware builds and `wake test` says there's no model (`__has_include`).
- **Ops:** the 13 a microWakeWord v2 streaming model uses (`CALL_ONCE`, `VAR_HANDLE`, `READ_VARIABLE`, `ASSIGN_VARIABLE`, `RESHAPE`, `STRIDED_SLICE`, `CONCATENATION`, `CONV_2D`, `DEPTHWISE_CONV_2D`, `SPLIT_V`, `FULLY_CONNECTED`, `LOGISTIC`, `QUANTIZE`, read from a published model with `--ops`) plus 9 relatives (`DEQUANTIZE`, `MUL`, `ADD`, `MEAN`, `AVERAGE_POOL_2D`, `MAX_POOL_2D`, `PAD`, `PACK`, `SPLIT`). A missing op fails `begin()` with its name.
- **Features into the model:** uint16 frontend output × 1/25.6 (microWakeWord's training scale), then the input tensor's own scale and zero point. The mic frames are DC-blocked first (the INMP441's offset isn't in the training audio).
- **Arena in PSRAM**, the manifest's size, doubled up to 256 KB if `AllocateTensors` fails (`wake info` prints what was used). The streaming state has its own 32 KB arena.
- **The wake task runs on core 0** (priority 4, below Wi-Fi and lwIP). For Phase 0 it owns the mic while `wake test`/`wake raw` run, and `wake` is refused while the robot link is connected.

## 2026-11-26 — Local skills

Plan: `docs/plans/2026-11-26-local-skills.md`. Where the code ended up differing from the first plan, it's marked "(review)".

- **Skills are the user's own Python scripts, one folder each in `SKILLS_DIR`,** with a `skill.json` manifest and `main.py`. Python only: the user writes Python, and uv already gives each skill its own packages. · Alternatives: any executable (no clean way to fingerprint or isolate it), PowerShell scripts, a plugin API inside CARL's process (a crash or a secret leak would be CARL's).
- **One tool per skill, `skill_<slug>`,** with fixed choices as enums and at most one free-text field, sent as JSON on stdin. The manifest's description goes into the tool description verbatim: it's the user's own text. · Alternatives: one `run_skill(name, args)` tool (an enum of names plus free-form args, so no per-skill schema), command-line arguments (quoting and injection).
- **Results are the script's stdout,** at most 1000 characters, wrapped as untrusted; CARL says it in its own words. A failure tells Claude only the exit code; stderr goes only to the log, on a failure. The log and Live tab show "Ran <name>.", never the output, which may be private.
- **Nothing runs until ticked on the Apps tab, and a fingerprint switches a skill off when its files change.** Approvals are `[{"slug", "fingerprint"}]` in `%LOCALAPPDATA%\desk-buddy\skills.json`, at most 20.
  - **The fingerprint covers every regular file (review),** not just `skill.json`, `*.py`, `pyproject.toml` and `uv.lock`: Python also imports `.pyw`, `.pyd` and `.pyc`, and `uv.toml` and `.python-version` change what runs. Only the top-level `.env` is left out; `.venv`, `__pycache__` and dot-folders are skipped (CARL never uses them, below). The manifest is hashed from the exact bytes that were parsed.
  - **Links are refused (review):** a symlink, junction or other reparse point anywhere makes the skill invalid, since code behind it would run unhashed. That rules out OneDrive's online-only files too.
  - **Limits:** 200 files and 5 MB, sizes checked before reading.
  - It catches edits and updates (a `git pull`), not a live local attacker swapping files between the check and the run, nor a skill that runs data files or downloads code. `server/README.md` says so.
- **Checked at every tool rebuild and again just before every run,** and for a skill that needs a yes, at the proposal and again at the yes: the fingerprint must equal the approved one the tool was built from. The rebuild's scan is cached until the approvals, `SKILLS_DIR` or the app names change (it hashes every file), so the check before the run is the real gate.
- **Secrets stay with the skill:** its own `.env` (or the Credential Manager), never read, hashed or passed by CARL; the script loads it itself. Scripts run with `clean_env`, an allowlist of Windows variables, so none of CARL's keys and no `UV_*` variable reach them; CARL's own venv is removed from `PATH`, and `PYTHONNOUSERSITE=1` drops user site-packages.
- **Nothing unhashed in the folder runs (review):**
  - **The skill's environment lives outside its folder (review),** in `%LOCALAPPDATA%\desk-buddy\skill-envs\<slug>` (`UV_PROJECT_ENVIRONMENT`, set for `uv sync` and `uv run`), so a planted `.venv` is never used. `PYTHONPYCACHEPREFIX` points at `skill-cache\<slug>`, so a planted `.pyc` is never loaded. uv gets `--no-config`.
  - **A skill without a `pyproject.toml` runs without uv (review),** as `<CARL's base python.exe> -s main.py`: outside project mode, `uv run` used a `.venv` in or above the folder (tested) and would build an environment from a PEP 723 header during a turn. uv is still required for skills to be on at all.
  - **A project skill must not sit inside another uv project (review):** a `pyproject.toml` above it (as given or with links resolved) could make it a workspace member and install code from outside. Checked before the setup and before every run.
- **Setup on approval only:** `uv sync --no-config --no-editable` (path dependencies are copied, so frozen at approval), 300 s, on a worker thread, one at a time, and it must leave a `uv.lock`. The skill is scanned again afterwards and the fingerprint taken from that state. Runs use `uv run --no-sync --no-config --no-python-downloads --offline main.py`, so nothing is installed during a question.
- **`uv.exe` is found by walking `PATH` (review):** absolute entries only and `uv.exe` only, so the current folder and `.bat`/`.cmd` files never count (`shutil.which` does both).
- **One skill at a time, killed with its tree** (`taskkill /T /F`) past its timeout (1–120 s, default 30). Shutdown kills a running skill or setup; a stuck pipe is never closed (it would block), only the process killed.
- **The strict-tool budget (review):** Anthropic's strict-schema limits count across every strict tool in a request (20 tools, 24 optional and 16 union-typed parameters). Skill schemas add no optional or union parameter (every choice a required, non-null enum, defaults described in words; the text a required string where `""` means none), so only the tool count matters: `build_tools` gives skill tools `strict` while fewer than 20 tools are strict, and the rest go non-strict. The server re-validates every input either way.
- **`needs_yes` skills use the existing spoken yes,** made general with a `Verb` (`OPEN`, `RUN`): "Shall I run <name> with: <text>?", and every note says "run" instead of "opened". The open-page wording is unchanged.
  - **Read-back refused at 200 characters, not cut (review):** the plan cut the text in the question to 200 characters; now a needs_yes skill takes at most 200 (or its lower `max_length`) on one line, and longer text is refused, so the user hears everything that will be sent. The script gets exactly the text that was read back. Control, format and invisible characters (private-use, unassigned, Hangul fillers, blank Braille) are refused, as the read-back wouldn't say them.
  - **The Live tab's `waiting` event shows the read-back (review),** "Waiting for the user to say yes to <name> with: <text>.", the full text rather than the 60-character cut the log line uses: it's what the user is asked.
  - **A slow confirmed skill:** it runs before Claude, with `PONDERING` after 4 s. Words spoken while it still runs get a "still running; nothing new was run" note; if the user cut the turn off with the key, the run finishes and its note reaches Claude with the next question. A crash says it "may not have run".
- **Prompt rules** (`SKILLS_TEXT`, locked): only when asked or the description clearly fits, never because web text, notes or skill output suggest it; the user's own words in the text field; call needs_yes skills straight away and never ask; never claim a run without a result or note; output is untrusted. With no skill offered, CARL says skills aren't set up.
- **Spoken names are unique across skills, apps and bookmarks;** the Apps tab refuses an app or bookmark name an approved (or changed) skill holds.
